# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Portal interno de Grupo Intra (Instituto de Atención Integral y Desarrollo Humano A.C.), construido por módulos. El proyecto se organiza en `apps/`: `apps/core` (autenticación, dashboard, permisos — el "núcleo" del portal) y un módulo de negocio por carpeta. Hoy hay tres módulos con código real: `apps/finanzas`, `apps/certificacion_intera` y `apps/portafolio`. Los módulos siguientes (RH, agenda, comunicados, etc.) se agregan de la misma forma, uno a la vez.

Stack: Django 5.2.10 (el docstring de `config/settings.py` dice 6.0.6 generado por scaffold, pero el paquete instalado es 5.2.10), Python 3.14, SQLite en desarrollo (`db.sqlite3`) y Postgres en Railway, sin frontend framework (HTML + CSS servidos vía Django templates/staticfiles).

Las dependencias están fijadas en `requirements.txt` (no hay `pyproject.toml`): Django, `dj-database-url`, `gunicorn`, `psycopg[binary]`, `requests`, `whitenoise`, `xhtml2pdf` (PDFs de Finanzas) y `openpyxl` (XLSX de Flujo de efectivo).

**Ojo con el repo de origen.** El remoto `origin` es `raltsito/plataforma_grupointra`, pero parte del trabajo llega desde `RocioMedC/plataforma_grupointra`. Si algo "no está" pero debería, verificar contra ese otro repo antes de asumir que falta:
`git fetch https://github.com/RocioMedC/plataforma_grupointra.git 'refs/heads/*:refs/remotes/rocio/*'`.

## Commands

```bash
# Run dev server
python manage.py runserver

# Migrations
python manage.py makemigrations
python manage.py migrate

# Create a superuser (necesario para entrar, no hay registro público)
python manage.py createsuperuser

# Tests (framework Django estándar). Ya hay suite real: apps/core/tests.py,
# apps/certificacion_intera/tests.py y apps/portafolio/tests.py.
python manage.py test
python manage.py test apps.certificacion_intera   # solo un módulo

# Portafolio: cargar/reparar instrumentos desde un Documento ya registrado
python manage.py importar_instrumentos_portafolio
python manage.py reparar_importaciones_instrumento
```

## Architecture

- **`config/`** — proyecto Django raíz (`settings.py`, `urls.py`, `asgi.py`, `wsgi.py`). `config/urls.py` incluye `apps.core.urls` en la raíz (`''`), `apps.finanzas.urls` bajo `finanzas/`, `apps.portafolio.urls` bajo `portafolio/` y `apps.certificacion_intera.urls` bajo `certificacion-intera/`. `admin/` es la otra ruta de nivel superior.
- **`docs/`** — documentos de diseño por módulo, escritos por el equipo, no generados: `PLATAFORMA_INTRA.md` (visión general), `INTERA.md`, `PORTAFOLIO.md`, `MODELO_DATOS.md`, `ENTREVISTA_1A1.md`, `INTEGRACION_CONSULTORIOWEB.md`, `CONTRATO_API_INTERA_CONSULTORIO_V1.md`, `UX_GUIDELINES.md`, `ROADMAP.md` y `DEUDA_TECNICA_CALCULADORAS_ADOLESCENTES.md`. Son la fuente de las **reglas de negocio y de los límites entre módulos** (qué le toca a quién). Leerlos antes de tocar `certificacion_intera` o `portafolio`; están escritos en futuro/prescriptivo, así que describen tanto lo ya construido como lo pendiente — verificar contra el código antes de dar algo por hecho.
- **`apps/`** — paquete contenedor de todas las apps del portal. Cada módulo de negocio vive en su propia carpeta (`apps/finanzas/`, y los que sigan). `apps/__init__.py` existe solo para que el paquete sea importable; no contiene lógica.
- **`apps/core/`** — una sola app Django (label `core`) que agrupa el núcleo del portal en sub-paquetes organizativos (no son apps Django separadas, no tienen su propio `INSTALLED_APPS`/migraciones):
  - `autenticacion/` — login, logout, recuperación de contraseña (usa las vistas genéricas de `django.contrib.auth.views`). `autenticacion/services.py` decide **a dónde cae cada quien al entrar**: `es_usuario_exclusivo_intera(user)` (grupos == exactamente `{'Certificación'}` y no superusuario) y `get_user_home_url(user)`, que manda a esos usuarios a `certificacion_intera:dashboard` en vez de al dashboard del portal.
  - `permisos/grupos.py` — `crear_grupos_sistema_intra` (migración de datos que crea los grupos base) y `usuario_pertenece_a(user, *nombres_grupo)`, el helper de RBAC que reutilizan los módulos de negocio (ej. `apps/finanzas`) en vez de repetir `user.groups.filter(...)` a mano.
  - `auditoria/` — bitácora del portal (RF-19), implementada. `auditoria/models.py::RegistroAuditoria` (registro de solo-agregar: usuario, fecha, generic FK al objeto, acción, campo, valor anterior/nuevo) y `auditoria/registro.py` con el único punto de entrada: `registrar(...)`, `registrar_cambio_de_campo(...)` e `historial_de(objeto)`. Vive en `core` y no en un módulo de negocio porque la van a consumir todos los módulos. Dos detalles no obvios: el modelo declara `app_label = 'core'` (el sub-paquete es organizativo, no una app Django) y se importa desde `apps/core/models.py` para que Django lo descubra; y `registrar()` **nunca propaga excepciones** — si la bitácora falla se escribe en el log, pero no se tumba la operación de negocio que la llamó. **Ojo: `certificacion_intera` no la usa.** Tiene su propia bitácora, `certificacion_intera/models.py::BitacoraProceso` (evento + descripción + usuario, colgada de un `ProcesoCertificacion`), visible en `certificacion_intera:proceso_bitacora`. Son dos bitácoras distintas conviviendo; si hay que consolidarlas algún día, es una decisión a tomar a propósito, no algo que arreglar de pasada.
  - `usuarios/`, `configuracion/` — reservados para el futuro (RF-20 catálogos administrables, perfil de usuario). Solo tienen un `__init__.py` con comentario, sin implementación.
  - El dashboard/launcher del portal (`dashboard_view`, `templates/core/dashboard.html`) vive en la raíz de `apps/core/`, no dentro de `usuarios/` — es el punto de entrada del portal, no un dato de perfil.
- **Roles vía `django.contrib.auth.Group`, no un modelo custom.** Los roles base (`Terapeutas`, `Recepción`, `Administración`, `Dirección`, `Sistemas`) se crean en `apps/core/migrations/0001_initial.py` vía `crear_grupos_sistema_intra` (`get_or_create`, idempotente). Los grupos de módulo se crean con su propia migración de datos: `Finanzas` en `apps/finanzas/migrations/0002_grupo_finanzas.py` y `Certificación` en `apps/certificacion_intera/migrations/0001_grupo_certificacion.py`. Si se necesita agregar/renombrar un rol, hacerlo con una nueva migración de datos, no editando una ya aplicada — `Certificación` también aparece en la lista de `crear_grupos_sistema_intra`, pero eso **no** lo crea en bases ya migradas (la 0001 de core ya corrió); quien lo crea de verdad es la migración de `certificacion_intera`.
- **Etiqueta visible ≠ nombre del grupo.** El grupo técnico es `Certificación`; en pantalla se llama "Coordinación INTERA". Al comparar permisos usar siempre el nombre del grupo.
- **Dashboard = sidebar con el catálogo de módulos del portal, no tarjetas sueltas.** `apps/core/configuracion/modulos.py` define `MODULOS` (los de "Centralización Intra" — Agenda, Finanzas, OrbitaEdu, OrbitaControl, RH, Capacitación, Mesa de Ayuda, Comunicados — más Certificación INTERA y Portafolio INTRA) y `modulos_para(user)`, que resuelve para cada uno si está `disponible` (requiere `construido=True` **y** pertenecer a alguno de sus `grupos`, vía `usuario_pertenece_a`) y por qué no lo está si no (`motivo_bloqueo`: `'proximamente'` si no está construido, `'sin_permiso'` si sí lo está pero el usuario no tiene el grupo). `apps/core/views.py::dashboard_view` solo llama `modulos_para(request.user)` y pasa el resultado al template — la lógica de permisos vive en `configuracion/modulos.py`, no en la vista. Los íconos SVG de cada módulo están en `apps/core/templatetags/core_extras.py` (tag `{% icono_modulo key color size %}`), reutilizados en el sidebar y en la grilla de módulos; una `key` sin entrada en `_ICONOS` cae a un círculo genérico — hoy le pasa a `portafolio`, que no tiene ícono propio. Tienen `construido=True` `finanzas`, `certificacion_intera` y `portafolio`; agregar un módulo nuevo es añadir una entrada a `MODULOS` (y, cuando exista de verdad, poner `construido=True` y su `url_name`).
- **Un usuario exclusivo de `Certificación` no puede ver el dashboard del portal.** `apps/core/views.py::dashboard_view` levanta `PermissionDenied` si `es_usuario_exclusivo_intera(request.user)` — su portal es el Panel INTERA, no la grilla de módulos. Consecuencia a tener presente: `logout_view` por GET redirige a `dashboard`, así que para ese usuario un logout por GET termina en 403 en vez de en el login (el logout normal es POST y sí funciona).
- **Login sin JS, POST normal.** `apps/core/templates/core/login.html` es solo la tarjeta (con el logo real de Grupo Intra) — el `<form>` hace un POST normal a `login_view`, que autentica y redirige directo a `/dashboard/`. Hubo una versión con animación de bienvenida (colapso de tarjeta + grilla de módulos + vuelo hacia el sidebar) implementada con `fetch` + JS; se quitó a propósito por decisión del usuario para simplificar — si se retoma en el futuro, cuidado con el bug que tuvo: una regla CSS de autor (`display: flex`) sobre un elemento con el atributo `hidden` gana sobre la regla `[hidden]{display:none}` del navegador, así que hace falta un selector explícito `.clase[hidden] { display: none; }` para que `el.hidden = true` funcione de verdad.
- **Autorización basada en pertenencia a grupos, resuelta fuera de la vista.** El patrón general del portal es: la lógica de qué grupos pueden ver qué vive en un catálogo o helper (no en el template), y las vistas solo lo consultan. Dentro de cada módulo de negocio, el control de acceso a las vistas usa `usuario_pertenece_a` (ej. `apps/finanzas/views.py::acceso_finanzas_requerido`).
- **`apps/finanzas/`** — primer módulo de negocio, con backend real (modelos + migraciones + Django admin), siguiendo la SRS interna (`SRS-FIN-001`). Modelos: `Ingreso`, `Egreso`, `Donativo` (captura manual de CFDI — folio, XML, PDF —, sin integración a un PAC todavía). Todas las vistas están protegidas por `acceso_finanzas_requerido` (grupo `Finanzas`, `Dirección` o `Sistemas`). Toda la captura tiene formulario propio dentro de la UI (modales); `/admin/` quedó como respaldo, no como la vía normal. Gráficos (barras, dona) son CSS puro (`conic-gradient`, alturas por `%`), no SVG ni JS — ver `apps/finanzas/static/finanzas/css/finanzas.css`. Filtro de plantilla `{{ valor|dinero }}` (en `apps/finanzas/templatetags/finanzas_extras.py`) formatea montos como `$1,234` / `-$1,234`.
- **Cada Ingreso y Egreso pertenece a una unidad: Intra o Academia (`models.py::Unidad`).** Intra es la operación clínica; Academia es la escuela. No son dos contabilidades separadas — el tablero (`finanzas:tablero`) tiene un selector Todos / Intra / Academia (`?unidad=`), y en "Todos" cada movimiento suma una sola vez. Los movimientos que captura un humano llevan un selector en el formulario (default Intra); los que genera el sistema traen la unidad fijada en código: sellar Nómina semanal/quincenal/administrativa → Intra, sellar Nómina Academia → Academia, importar el Reporte de Recepción → Intra, y un `Ajuste` **hereda** la unidad del registro que corrige (si no, el tablero filtrado deja de cuadrar). Los `Donativo` NO tienen unidad a propósito: son institucionales, así que se muestran igual en las tres vistas del tablero (el KPI lo dice) y no aparecen en "Movimientos recientes" cuando hay filtro activo. La migración `0013` clasificó lo ya capturado: egresos de categoría `nomina_academia` y los ingresos de diplomado/taller/curso pasaron a Academia, todo lo demás quedó en Intra; de ahí en adelante la unidad **no se infiere del concepto**, se elige a mano.
- **Los tres reportes descargables de `finanzas:reportes` piden un periodo antes de generarse.** Los tres recuadros de "Generar reportes" (Estado de resultados → PDF, Flujo de efectivo → XLSX, Concentrado de donativos → PDF) son `<button>` que abren **un solo** modal; el script al final de `reportes.html` le pone el `action` según el `data-url` del botón que se picó. El modal manda `periodo=todo` o `periodo=rango&desde=…&hasta=…`, y los campos de fecha nacen `disabled` a propósito: así "todo el historial" no depende de que el usuario los vacíe. Del lado del servidor, `reportes.py::rango_pedido` devuelve `(None, None)` para todo el historial, endereza un rango invertido e ignora fechas inválidas — ningún caso devuelve error, siempre sale un documento.
- **La lógica de los reportes vive en `apps/finanzas/reportes.py`, y el criterio de "dinero real" en `apps/finanzas/totales.py`.** `totales.py` (ingresos/egresos/donativos efectivos) se extrajo de `views.py` justo para que la pantalla y el documento descargado no puedan discrepar; `views.py` conserva alias privados (`_ingresos_efectivos = ingresos_efectivos`) para no reescribir sus decenas de llamadas. `reportes_view` y el PDF del Estado de resultados llaman ambos a `reportes.py::estado_de_resultados(desde, hasta)`: si se agrega un renglón, se agrega una sola vez.
- **Cuidado con las celdas vacías en los templates de PDF.** Un `<td></td>` literalmente vacío hace que xhtml2pdf ignore el ancho declarado de esa columna, la encoja al mínimo y pinte los fondos de las filas fuera de la tabla (se ve como bandas de color que se salen y una tabla angosta). Las celdas sin dato tienen que llevar `&nbsp;`. Está anotado dentro de `estado_resultados_pdf.html` y `donativos_pdf.html`.
- **El pago a terapeutas se hace SOLO por Nómina; `Honorario` y `Tabulador` están retirados.** Hubo un segundo camino para pagarle a un terapeuta: `Honorario` (categoría A/B/C + bono, calculado contra `Tabulador`), capturado a mano en la pantalla "Egresos y Honorarios". Convivía con `LineaNominaSemanal` sin ninguna validación cruzada, así que un mismo terapeuta se podía pagar dos veces en el mismo periodo — uno por cada camino — y el Estado de resultados los sumaba en dos renglones distintos. Se retiró el 2026-07-31 (decisión del usuario) porque la nómina semanal ya trae los montos ya calculados de ConsultorioWeb (`subtotal_sesiones` / `total_bonos` / `total_pago`) y el `Tabulador` no participa en ese cálculo. Los modelos `Honorario` y `Tabulador` siguen existiendo en `models.py` y en las migraciones, pero **ya no tienen UI, formulario, admin ni referencia desde ninguna vista**, y sus tablas se vaciaron. Si vuelve a hacer falta un tabulador propio de Finanzas, replantearlo dentro de Nómina, no resucitando `Honorario`. La pantalla se llama ahora solo "Egresos" (`finanzas:egresos`, `egresos_view`, `finanzas/egresos.html`).
- **Nómina: el sellado es del documento, no del egreso.** `NominaSemanal` (cabecera: tipo semanal/quincenal/administrativa, periodo, fecha de pago, estado **Borrador → Sellada**, usuario que genera) + `LineaNominaSemanal` (una persona, con los tres conceptos separados que pide la sección 3.1 del documento de requerimientos: `pago_base`, `vale_gasolina` — que según Administración es lo mismo que el bono — y `extras`). La lógica vive en `apps/finanzas/nomina_semanal.py`. **Los Egresos no se crean al sincronizar, sino al sellar** (`sellar_linea` / `sellar_periodo`), que es lo que permite revisar y corregir antes de que el movimiento sea definitivo; una corrección posterior al sellado es un `Ajuste`, no una edición. Misma estructura en Academia (`NominaAcademia.estado`, `sellar_nomina_academia`, `sellar_periodo_academia`). Ojo con la distinción: `estado` es el ciclo de vida del documento (Borrador/Sellada) y `estatus` es el del dinero (Pendiente/Pagado) — son dos cosas distintas a propósito.
- **`LineaNominaSemanal.montos_editados`** es la bandera que evita que una re-sincronización con ConsultorioWeb pise un monto que Finanzas ya corrigió a mano. Los datos que no son decisión de nadie (citas atendidas, desglose por paciente, ingreso generado) sí se siguen refrescando en cada sincronización.
- **La pantalla de Nómina auto-sincroniza solo la primera vez** que se abre un periodo semanal (si `CONSULTORIOWEB_API_URL` está configurado). En las visitas siguientes no vuelve a llamar a la API — sería lento en cada recarga; para eso está el botón "Sincronizar ahora". El sellado del lado de ConsultorioWeb todavía no dispara un webhook.
- **`apps/portafolio/` es la biblioteca de recursos reutilizables; `apps/certificacion_intera/` es el proceso de negocio que los consume.** Esa separación es la regla de arquitectura central de los dos módulos (ver `docs/PORTAFOLIO.md`), y vale la pena respetarla al agregar código:
  - **Portafolio es dueño de la estructura**: `Documento` → `Instrumento` → `PreguntaInstrumento`/`SeccionInstrumento`, más `CalculadoraInstrumento`, `RevisionInstrumento`, `PlantillaPDF`, `Reporte` y `RecursoCompartido`. Todo `Instrumento` nace de un `Documento`; toda `Pregunta` pertenece a un `Instrumento`.
  - **INTERA es dueño de lo individual**: `Escuela`, `ProcesoCertificacion`, `Participante`, `AplicacionInstrumento`, `RespuestaInstrumento`, `ResultadoInstrumento`, `EntrevistaUnoAUno`, `Consejeria`, `Canalizacion`, `SolicitudAtencion` y `BitacoraProceso`.
  - En corto: **Portafolio nunca sabe qué participante respondió qué**, e INTERA nunca crea instrumentos ni preguntas ni implementa lógica de calificación propia. Si hace falta una regla de cálculo nueva, va en Portafolio.
- **Toda la lógica de calificación vive en `apps/portafolio/services_calificacion.py`, y su único punto de entrada es `calcular_resultado(...)`.** Ese archivo tiene una calculadora por instrumento (`_calcular_scid2`, `_calcular_scl90`, `_calcular_dass21`, `_calcular_tds`, `_calcular_tci`, `_calcular_raven`, `_calcular_isra`, `_calcular_allport`, más las variantes adolescentes) y tres piezas de resolución que conviene conocer antes de tocarlo: `_ALIAS_CLAVES` (normaliza `scid-ii`/`scid_ii`/`scid` → `scid2`), `_CONTEXTOS_REQUERIDOS` (qué dato demográfico exige cada clave — `fecha_nacimiento`, `sexo`) y `_VARIANTE_POR_CLAVE_EXACTA` (adulta vs. adolescente). El consumidor solo manda respuestas + contexto y recibe el resultado.
- **`CalculadoraInstrumento.Estado` no es un on/off, y los cuatro valores tienen consecuencias distintas.** `ACTIVA` (validada), `ORIENTATIVA` (se ejecuta **pero marca `requiere_revision_profesional` y arrastra las advertencias** `ADVERTENCIA_RESULTADO_ORIENTATIVO` / `ADVERTENCIA_CORTA_...`), `NO_DIAGNOSTICA` (se ejecuta, sin diagnóstico) y `BLOQUEADA` (no se ejecuta). Lo resuelve `_metadatos_estado_revision`. **Ningún resultado debe presentarse como diagnóstico** ni disparar acciones automáticas: es una restricción clínica del proyecto, no un detalle de UI. `docs/DEUDA_TECNICA_CALCULADORAS_ADOLESCENTES.md` explica qué falta aprobar antes de automatizar el protocolo de reactivos críticos de Plutchik (13, 14 y 15) — no inventar contactos, mensajes ni escalamientos ahí.
- **La Entrevista 1:1 está partida a propósito entre los dos módulos.** La *estructura* (secciones MOT/DES/RES/MOD, preguntas, condicionales, versión) es de Portafolio: `apps/portafolio/services_entrevista.py`, clave `entrevista-1a1`, cargada por la migración `portafolio/0004_cargar_plantilla_entrevista_1a1.py`. La *aplicación* es de INTERA: `apps/certificacion_intera/services_entrevista_1a1.py` + `views_entrevista_1a1.py` (`EntrevistaUnoAUno`, `RespuestaEntrevistaUnoAUno`, `HistorialEntrevistaUnoAUno`, `VerificacionAccesoEntrevista`). Es privada y asistida: exige instrumentos obligatorios finalizados y fecha de nacimiento (`requisitos()`), y valida identidad con intentos limitados por `ENTREVISTA_1A1_MAX_INTENTOS`, `ENTREVISTA_1A1_VENTANA_INTENTOS_MINUTOS` y `ENTREVISTA_1A1_AUTORIZACION_MINUTOS` en `settings.py`.
- **INTERA tiene rutas públicas sin login, y son las únicas.** `certificacion-intera/aplicar/<uuid:token>/` (batería completa del proceso) y `certificacion-intera/aplicaciones-individuales/<uuid:token>/` (un instrumento). Van por UUID, no crean cuentas, vinculan o crean al participante por matrícula dentro del proceso, y piden una sola aceptación del aviso de privacidad antes del envío definitivo. **Todo lo demás pasa por `acceso_certificacion_intera_requerido`** (`views.py`, grupos `Certificación`/`Dirección`/`Sistemas`), que `views_extra.py` y `views_entrevista_1a1.py` importan desde `views.py` en vez de redefinir. Portafolio usa el suyo, `acceso_portafolio_requerido` (mismos tres grupos).
- **Hay DOS integraciones distintas con ConsultorioWeb y no comparten ni settings ni esquema de autenticación.** No mezclarlas:
  | | Finanzas (nómina) | Certificación INTERA (solicitudes de atención) |
  |---|---|---|
  | Código | `apps/finanzas/integraciones/consultorioweb.py` | `apps/certificacion_intera/consultorio_web.py` |
  | URL | `CONSULTORIOWEB_API_URL` | `CONSULTORIOWEB_API_BASE_URL` |
  | Timeout | `CONSULTORIOWEB_TIMEOUT` (45s) | `CONSULTORIOWEB_API_TIMEOUT` (10s) |
  | Interruptor | — (basta con que la URL exista) | `CONSULTORIOWEB_INTEGRATION_ENABLED` (default `False`) |
  | Cabecera | `X-API-Key: …` | `Authorization: ApiKey …` |
  Lo único compartido es `CONSULTORIOWEB_API_KEY`. El contrato de la parte de INTERA está en `docs/CONTRATO_API_INTERA_CONSULTORIO_V1.md`.
- **Password reset apunta a templates que no existen todavía.** `apps/core/autenticacion/urls.py` referencia `core/password_reset_sent.html`, `core/password_reset_form.html` y `core/password_reset_done.html`, pero solo `apps/core/templates/core/password_reset.html` existe en el repo. El flujo de "olvidé mi contraseña" romperá en producción hasta crear esos tres templates (gap preexistente, no introducido por la reestructura a `apps/`).
- **Email backend está en modo consola.** `config/settings.py` configura primero SMTP de Gmail con credenciales placeholder y luego sobreescribe `EMAIL_BACKEND` a `django.core.mail.backends.console.EmailBackend` — los correos de recuperación de contraseña se imprimen en consola, no se envían de verdad, hasta que se configure un correo institucional real.
- **Estáticos y templates son por-app**, bajo `apps/<app>/static/<label>/` y `apps/<app>/templates/<label>/` (convención estándar de Django vía `APP_DIRS`, no hay carpeta `static/`/`templates/` global). Nota: el `label` de cada `AppConfig` (`core`, `finanzas`, `certificacion_intera`, `portafolio`) es lo que determina la carpeta de templates/estáticos, no el nombre de la carpeta física — por eso `apps/core/templates/core/...` y no `apps/core/templates/apps.core/...`.
- **Los módulos de negocio usan herencia de templates** (`{% extends %}`/`{% block %}`) vía su propio `_base.html` (`finanzas/_base.html`, `certificacion_intera/_base.html`, `portafolio/_base.html`), para no duplicar sidebar/header en cada vista. Las pantallas de `core` (login, dashboard, password reset) siguen sin herencia: cada template es un documento HTML independiente.
- **URLs de los módulos de negocio usan namespace** (`app_name` en su `urls.py`) — `{% url 'finanzas:tablero' %}`, `{% url 'certificacion_intera:dashboard' %}`, `{% url 'portafolio:dashboard' %}`. Las de `apps/core` siguen siendo planas (`login`, `dashboard`, `logout`) para no romper `LOGIN_URL`/`LOGIN_REDIRECT_URL` en `settings.py`.
- **El estilo de código no es uniforme entre módulos, y está bien así — no "normalizar" de paso.** `apps/certificacion_intera` y `config/settings.py` usan un formato de líneas muy cortas (un argumento por renglón); `apps/portafolio/views.py` usa el opuesto (vistas de una sola línea, diccionarios de contexto enormes en línea); `apps/core` y `apps/finanzas` son el estilo original. Al editar, seguir el estilo del archivo que se está tocando. Reformatear un archivo completo entierra el cambio real en el diff — ya pasó con `config/settings.py`, cuyo reformateo se llevó de corbata varios comentarios que explicaban el *por qué* de decisiones (entre otros, por qué `CONSULTORIOWEB_*` no tiene default: para que falle ruidoso si falta la variable en Railway).
- **Cuidado: desarrollo usa SQLite y producción usa Postgres.** Hay errores que pasan las pruebas locales y solo revientan en Railway. Ya mordió dos veces:
  1. **Largo de los CharField.** SQLite no lo valida, Postgres sí (`DataError: value too long`). Cualquier texto armado a mano que vaya a un campo con `max_length` (ej. `Egreso.concepto`, que junta etiqueta + nombre de persona + periodo) debe pasar por `apps/finanzas/textos.py::concepto_egreso`.
  2. **`select_related` de una relación opcional junto a `update_or_create`/`select_for_update`.** El `SELECT ... FOR UPDATE` más el LEFT OUTER JOIN que provoca el `select_related` hacen que Postgres responda *"FOR UPDATE cannot be applied to the nullable side of an outer join"*. SQLite ignora el `FOR UPDATE` y no se entera.
  Al tocar consultas o textos generados, vale más verificar contra producción (`railway ssh "/opt/venv/bin/python manage.py shell -c ..."`) que confiar en que la prueba local pasó.
- **Los errores 500 de producción se ven en `railway logs`** gracias a `LOGGING` en `config/settings.py`. Sin esa configuración, el handler de consola de Django está filtrado por `require_debug_true` y con `DEBUG=False` los tracebacks no llegan a ningún lado — el síntoma es "Server Error (500)" en pantalla y logs que solo muestran el arranque de gunicorn. No quitar esa configuración.
